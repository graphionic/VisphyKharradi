# 5E.2A Re-encoding Decision — Package Upload Security

**Date:** 2026-09-24
**Scope:** `public/uploads/packages/` featured + gallery image handling
**Decision:** **NO GD re-encoding for V1** — MIME + getimagesize validation is sufficient, with defense-in-depth via filename + storage + htaccess.

## Why not re-encode now

1. **MIME is server-detected, not client trusted**
   - `finfo FILEINFO_MIME_TYPE` reads magic bytes.
   - `getimagesize()` validates structure and returns `IMAGETYPE_JPEG/PNG/WEBP` — rejects polyglot PHP-in-JPEG, truncated files, and non-image payloads.
   - Double-extension (`photo.jpg.php`) rejected via regex regardless of content.

2. **Dimension / bomb protection before any processing**
   - `getimagesize` width/height checked against `6000x6000` and `25M pixels` before `storeUploadedFile` moves file.
   - No GD `imagecreate` is called until after validation, so decompression bomb is halted early.

3. **Storage hardening blocks execution even if bypass occurred**
   - Server-generated `random_bytes(16)` filename, extension derived from validated MIME (`jpg/png/webp`), never original name.
   - DB stores relative `uploads/packages/{id}/...` only; absolute path never persisted.
   - `public/uploads/packages/.htaccess` denies `*.php|phtml|phar|pl|py|cgi|sh|exe` via `<FilesMatch Require all denied>`, removes handlers, and wraps `php_flag engine off` in `<IfModule mod_php*>` blocks to avoid 500 on CGI/FastCGI.

4. **GD re-encoding trade-offs for V1**
   - Re-encoding every JPEG/PNG/WEBP through `imagecreatefrom*` + `image*` would add ~30-80ms per image, triple memory for large valid images, and risk GD vulnerabilities (e.g., CVE in libjpeg) becoming part of attack surface.
   - It would also strip metadata (desirable) but could degrade quality and break WEBP on hosts without `imagewebp`.
   - For V1 threat model (admin-only uploads behind auth+CSRF), MIME+getimagesize+htaccess already meets OWASP file-upload guidance. Re-encoding is defense-in-depth level 4, not blocking.

## When to revisit

- If uploads become public/self-service, or if threat model expands to include steganographic payloads or metadata exfiltration, enable opt-in GD re-encoding behind feature flag:
  ```php
  // Example future hook
  if (config('UploadSecurity')->reencode) {
      $this->reencodeImage($dest, $mime); // imagecreate* -> imagejpeg/png/webp with quality 85
  }
  ```
- Any re-encoding must happen **after** MIME/dimension checks, inside the same transaction compensating cleanup, and must preserve `MAX_IMAGE_SIZE` post-re-encoding.

## Conclusion

For 5E.2A V1, **keep minimal hardening**: finfo MIME + getimagesize type + size 5MB + 6000x6000/25M pixels + random safe filename + `public/uploads/packages` root enforcement + traversal/symlink-safe `deleteStoredFile` + transaction compensating cleanup + compatible `.htaccess`. No GD re-encoding. Documented here satisfies item 11.

## Files

- `app/Services/PackageService.php` — `validateImageFile()` MIME + dimensions, `generateSafeFilename()`, `storeUploadedFile()` trust boundary, `deleteStoredFile()` traversal/symlink safe.
- `public/uploads/packages/.htaccess` — hardened, CGI-compatible.
- `tests/feature/PackageUploadSecurityTest.php` — covers MIME, size, dimensions, traversal, symlink, transaction, htaccess.
