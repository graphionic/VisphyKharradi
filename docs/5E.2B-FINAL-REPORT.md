## B — Gallery Ownership Findings

**Finding:** `updatePackageWithMedia` performed ownership check `if (!isset($existingMap[(int)$eid])) throw` but:
- Cast `(int)$eid` on array/object produced `0` with PHP warning, not clean error.
- Duplicate IDs `[5,5]` passed `isset` twice, then updated same row twice with `display_order` 1 then 2 (final 2) — should be rejected.
- Malformed `0/-1/abc/1.5` via `(int)` cast to `0/ -1/0/1` inconsistently, no explicit `ctype_digit` check, no duplicate detection.
- Nested array `[[5]]` caused `is_array` to be cast to 0, silent.
- `galleryOrder` was filtered via `array_filter(... in_array retained)` — cross-package ID in `galleryOrder` was **silently ignored** instead of explicitly rejected, and duplicate order not checked.
- `existingGalleryAlt[$idx]` cast `(string)$alt` on array triggered `Array to string conversion` warning, not sanitized to plain.
- Early gallery limit `count($nonEmpty)+count($existingGalleryIds)` counted duplicates and empty strings, not unique final state.
- Controller `existing_gallery_ids` handling via `array_filter` kept nested arrays, passed to service with warnings.

**Severity:** CRITICAL — gallery ID alone trusted, cross-package keep/remove/reorder/alt possible if ownership bypassed.

## C — Cross-Package Tampering

**Attack scenario tested:**
- Package A gallery `id=10`, Package B gallery `id=20`. While editing A, submit `existing_gallery_ids = [...A..., 20]` or `gallery_order = [20, ...]` or `existing_gallery_alt` for `20`.

**Expected:** Package B media **must remain completely unchanged**, request rejected safely (error `gallery_images`, no warnings, no SQL errors, no file deletion).

**Hardening:**
- **New helpers:**
```php
private function sanitizeAltText(mixed $alt): ?string { if (is_array||is_object) return null; trim((string)); mb_substr 0,300; }
private function sanitizeOriginalName(mixed $name): ?string { similar 255; }
private function validateGalleryIds(array $ids, array $existingMap): ?string {
  foreach ids: if (is_array||is_object) return 'Invalid gallery selection.';
                 str=trim((string)id); if (!ctype_digit(str)|| (int)str<=0) return 'Invalid gallery selection.';
  if (count(intIds) !== count(array_unique(intIds))) return 'Invalid gallery selection. Duplicate IDs.';
  foreach intIds if (!isset($existingMap[int])) return 'Invalid gallery selection.'; // cross-package/unknown/deleted
  return null;
}
private function validateGalleryOrder(array $order, array $retainedIds): ?string {
  similar ctype_digit, >0, unique, every order id must be in retainedIds else 'Invalid gallery order.'
}
```
- In `updatePackageWithMedia`:
  - Early `unset($input['remove_path'], $input['image_path'], ...)` distrust.
  - Normalize `existingGalleryIds`/`galleryOrder` to arrays, validate via helpers **before** `transStart`.
  - Filter empty strings `array_filter(... !=='' && !==null)` then validate; duplicates now rejected.
  - Ownership check now via `validateGalleryIds` covering zero, -1, abc, 1.5, nested arrays, unknown 999999, deleted record, cross-package — all return `gallery_images` error, no warnings, no SQL.

**Tests (4):**
- `testCrossPackageGalleryKeepAttack` — A(2) + B(1), submit A+ B's ID → `assertFalse` `gallery_images`, B `count 1` unchanged, A `count 2` unchanged, files exist.
- `testCrossPackageGalleryRemoveAttack` — submit B's ID as sole retained for A → rejected, `assertFileExists` B image.
- `testCrossPackageGalleryReorderAttack` — order `[B, A]` → rejected, B order unchanged, A order unchanged.
- `testCrossPackageAltTextAttack` — submit B's ID with alt `hacked` via A → rejected, B `alt_text` unchanged.

All assert no `SQL` in errors, no warnings, no cross mutation.

## D — Client Path Trust Audit

**Finding:** Spec requires: featured removal via `remove_featured_image=1` intent only; server obtains actual `featured_image` path from `packages` DB row. Gallery removal via `gallery record ID` only, server loads `package_gallery_images` and verifies `package_id` ownership, then determines `image_path` itself. Browser must never submit `remove_path`/`image_path`/`featured_image` as authoritative deletion path, nor `../../` traversal.

**Audit:**
- **Controller before:** `store`/`update` read `remove_featured_image` boolean, `existing_gallery_ids` IDs, `gallery_order`, `existing_gallery_alt` — did **not** read `remove_path`/`image_path`. Good base, but no explicit `unset` — malicious `POST remove_path=../../.env` would be ignored implicitly but not documented, and `$_POST['featured_image']` as string could be mistaken for file.
- **Service before:** `updatePackageWithMedia` used `$oldFeatured = $existing['featured_image']` and `$oldFilesToDelete[] = $g['image_path']` from DB, never from `$input`. Good, but `$input` still contained `featured_image` string if attacker sent it, though `validateCreate` ignored unknown fields.

**Hardening:**
- **Controller:** Explicit `unset($input['remove_path'], $input['image_path'], $input['featured_image'], $input['featured_image_path'], $input['gallery_path'], $input['gallery_image_path'], $input['remove_featured_path'])` plus `unset($_POST['remove_path'])` etc. In `store` and `update` both. Added `if (is_string($_POST['featured_image'])) unset` guard. Documented comment `5E.2B: CLIENT MUST NOT CONTROL FILE PATH`.
- **Service:** First line `unset($input['remove_path'], $input['image_path'], $input['featured_image'], ...)` — defense in depth. Featured logic now comment `FEATURED OWNERSHIP: old path from DB only, never from client`.

**Test:**
- `testClientControlledPathIgnored` — creates package with featured, then calls `updatePackageWithMedia` with `remove_path=../../.env`, `image_path=uploads/packages/.../evil.jpg`, `featured_image=../../.env` in `$input` plus `removeFeatured=true` → asserts `success true`, `featured_image null` via intent, `assertFileDoesNotExist` old featured, `assertFalse(is_file(FCPATH.'../../.env'))` outside not touched. Second part via HTTP `POST /admin/packages/{id}` with `remove_featured_image=1`, `remove_path`, `image_path`, `featured_image` string → `assertRedirect`, `assertNull` featured, file deleted, outside preserved. Ensures `image_path` submitted is ignored, deletion uses DB `image_path`.

## E — Gallery Limit Logic

**Requirement:** Max 10 per package, server must calculate **FINAL** state correctly, not just uploaded files.

- `9 existing +1 new → allowed`
- `10 existing +1 new → rejected`
- `10 existing -2 removed +2 new → allowed`
- `10 existing -1 removed +2 new → rejected`

**Finding before:** Early check `count($nonEmpty)+count($existingGalleryIds) >10` counted raw `existingGalleryIds` length (including duplicates/empty) and did not handle `10-2+2` correctly if `existingGalleryIds` were filtered after? It also checked `count($existingGalleryIds) >10` alone.

**Hardening:**
- After ownership validation, compute `retainedCount = count(array_unique(array_map('intval', $existingGalleryIds)))` (unique, after filtering empty strings).
- `nonEmptyCount = count($nonEmptyGalleryFiles)` (filtered `UPLOAD_ERR_NO_FILE`).
- `finalCount = retainedCount + nonEmptyCount; if ($finalCount > MAX_GALLERY_COUNT) return error`.
- Also `if ($retainedCount > MAX)` check.
- This correctly handles `9+1=10` allowed, `10+1=11` rejected (`retained 10 +1`), `8+2=10` allowed (`retained 8 +2`), `9+2=11` rejected.
- Duplicate IDs now rejected earlier via `validateGalleryIds`, so not counted as separate.
- Controller's `array_filter` for empty strings already, service re-filters.

**Tests (4):**
- `testGalleryLimit9Plus1Allowed` — 9 → keep 9 +1 new → `assertTrue` `count 10`.
- `testGalleryLimit10Plus1Rejected` — 10 → keep 10 +1 new → `assertFalse` `gallery_images`, `count 10` unchanged.
- `testGalleryLimit10Minus2Plus2Allowed` — 10 → keep 8 +2 new → `assertTrue` `count 10`.
- `testGalleryLimit10Minus1Plus2Rejected` — 10 → keep 9 +2 new → `assertFalse` `count 10` unchanged.

All via service direct, files cleaned.

## F — Gallery Ordering

**Spec:** Submitted sequence may determine order. Server must validate ownership, uniqueness, derive `display_order` sequentially 1,2,3… Do not trust posted `display_order` values. No gallery record belonging to another package may enter sequence.

**Finding before:** `orderedRetained = array_values(array_filter($orderIds, fn(... in_array retained)))` silently dropped cross-package IDs, no error; duplicate order IDs would be kept (update same row twice). `display_order` was derived via `$gSeq =1; foreach orderedRetained` which is correct sequential, but `retainedIds` duplicates allowed.

**Hardening:**
- `validateGalleryOrder` now rejects duplicate order IDs (`Duplicate IDs.`), non-ctype_digit, and any order ID not in `retainedIds` (`Invalid gallery order.`).
- Order IDs are `array_map('intval', $orderIds)` filtered to retained, then `array_unique`, then fallback to `existingGalleryIds` order if count mismatch, then sequential `gSeq`.
- Never reads `$_POST['display_order']` values; only derives.
- Stored via `update((int)eid, ['display_order'=>$gSeq++])` — server-controlled.

**Tests:**
- `testGalleryOrderSequentialServerControlled` — 3 images `ids=[1,2,3]`, reorder to `reversed [3,2,1]` → `assertTrue`, `assertEquals($reversed, array_column(after))`, each `display_order idx+1`. Second submit `dupOrder [1,1,2]` → `assertFalse` duplicate order rejected, gallery unchanged.
- Also verified cross-package reorder attack already (section C) rejected.

## I — Zero-FK Media Integrity

**Spec:** Audit `package_gallery_images.package_id`. Valid: references existing active **or** soft-deleted package (deleted media intentionally preserved). Invalid true orphan: points to no package row at all. Detect true orphans in test/audit DB. Do NOT auto-delete production data.

**Finding:** `package_gallery_images` has indexes but **no FK** (intentional). `deletePackage` soft deletes, `restorePackage` restores — gallery preserved. No orphan creation via normal flow. But direct DB insert with `package_id=999999` would create orphan.

**Hardening:**
- Added audit helpers:

```php
public function findOrphanGalleryRows(): array {
  $db->table('package_gallery_images g')->join('packages p','p.id=g.package_id','left')->where('p.id IS NULL')->get()->getResultArray();
}
public function hasOrphans(): bool { return count(findOrphan...)>0; }
```
- `deletePackage` and `restorePackage` still preserve media, not orphan.

**Tests:**
- `testTrueOrphanDetection` — initially `assertCount(0, findOrphan)`. Clean via `where package_id 9999999 delete` → `assertCount(0)`. Then create package with gallery, delete package via `deletePackage`, `assertCount(0, findOrphan)` — deleted media not orphan.

## L — Transaction Integrity

**Spec:** Review gallery DB synchronization during Edit. Failure while adding/removing/reordering/changing alt text must rollback gallery DB state consistently. Filesystem cleanup rules from 5E.2A remain unchanged (new files cleaned on failure, old preserved until commit).

**Audit:**
